# Findings: editor-image-library

**日時:** 2026-08-01
**対象:** plans/editor-image-library/（US-08 画像自身の公開状態可視化 + F-02 検出外参照宣言の文言 + F-03 メタデータ欄への統合サイクル）
**統合先:** plans/editor-image-library/problem.md v7（F-01・F-02 を統合。F-03・F-04 は次サイクルの申し送りとして問題定義に記載。F-05〜F-08 は tdd-skills への申し送りのため未統合）

## 操作の事実

- 検証用にリモート（GitHub）へ push し、ブランチのトラッキングを設定した
- 画像ライブラリのサイドバーを確認し、公開状態が記事一覧と同じ記号方式で表示されることを確認した
- どの画像も公開されていなかったため、`shiba-inu.jpg` を `book/to/new.md` に読み込ませ、`book/to/new.md` を「公開する」で公開した。`shiba-inu.jpg` が「公開済み」と表示されることを確認した
- `shiba-inu.jpg` を `shiba-inu.jpeg` にリネーム（移動）し、公開状態の表示を確認した。表示は「公開済み」のまま変化しなかった
- `book/to/new.md` 側の表示は「変更あり」になっていた
- 実際のgitの状態を確認しに行った（`src-sample/image/shiba-inu.jpg` が未コミットの削除、`src-sample/image/shiba-inu.jpeg` が未コミットの追加）
- `book/to/new.md` を再度「公開する」で同期した。push コミット（`b925ef9`）を確認したところ、`shiba-inu.jpeg` は追加されたが `shiba-inu.jpg` は削除されておらず、現在のリモート追跡ブランチのツリーにも残存している（`git show b925ef9:src-sample/image/shiba-inu.jpg` で存在確認済み）
- F-02（検出外参照宣言のチェックボックス）・F-03（メタデータ欄内のファイル名インライン編集・削除操作）を操作した

## 利用仮説の照合

- **US-08 S1（画像自身の公開状態を確認できる）**: 期待どおり。サイドバー・詳細で記事一覧と同じ記号表示を確認できた
- **US-08 S2（記事の公開・非公開の結果が画像の公開状態に反映される）**: 移動を伴わない単純な公開では期待どおり。移動（改名）を挟んだ場合は外れ側——表示が「公開済み」のまま変化せず、リネーム後・再同期後も旧ファイルがリモートに残るという実体との対応が取れず、利用者自身も画面から真偽を判断できなかった。利用仮説が想定していた「外れ」（同期直後の再取得タイミングのズレ）とは異なる種類のズレ（移動によって生じる恒久的な不整合）だった
- **US-08 S3（画像自身と参照記事の状態を混同しない）**: 記事側「変更あり」・画像側「公開済み」という異なる表示自体は混同していないが、二つの表示の関係を読み解けなかった
- **F-02（検出外参照の宣言を、振る舞いが伝わる文言で判断できる）**: 外れ。チェックボックスの説明文（「参照がなくても非公開にしない」）自体は効果を説明しているが、見出し「検出外参照」がそのまま残っており、作成者自身も見出しの意味を即座に理解できなかった
- **F-03（操作を一つの欄でまとめて行える）**: 期待どおり。ファイル名インライン編集・削除操作はメタデータ欄で完結し、わかりやすいという評価だった

## 印象（ユーザーの言葉）

- 「判断がつかなかった。それで、実際のgitの状態を確認しにいった」
- 移動後に自然だと思う表示は「更新あり」状態（現在の公開済み/未公開の二値ではなく）
- 「『更新あり』では git mv 扱いになるのが自然だとは思う。ただし、gitを知らないユーザーにはあまり関係がないかもしれないが、リネーム前の画像はリモートでは公開のまま残ることになるとおもうし、それを知覚・操作する術がない」
- 「検出外参照」という文言について:「一般ユーザーにはやっぱり意味がよくわからないとおもう。というかわたしにもパッと意味はわからない」。具体案:「検出外参照」という見出しを作らず、[公開状態] の見出し配下に「公開済み」の表示と「[]非公開にしない」チェックボックスとして統合する
- メタデータ欄統合（ファイル名インライン編集・削除）は「実際に試して、わかりやすいとおもいます」
- 削除ボタンについて:「やたら横長になっているので、ボタンサイズを文言とフィットさせ、適当なパディングを入れ、左寄せにしたほうが良いかな」

## 発見

### F-01: 移動（改名）操作は台帳の公開済み参照をそのまま引き継ぐため、実体を確認しないまま「公開済み」と表示され続ける

**戻し先:** /tdd-problem（同一 plan）
**出どころ:** 利用インタビュー・成果物レビュー（`packages/editor/server/imageLedger.js` の `renameEntry`、`packages/editor/server/move_image.js`）
**解釈・原因の仮説:** `renameEntry` は台帳エントリ（`publishedReferredBy` を含む）を新しいキーへそのままコピーするだけで、リモートへの実際の反映は行わない。公開状態インジケーターは台帳の値をそのまま表示するため、移動直後は「まだ同期されていない」という状態を区別できない。problem.md の「解決したと言える状態」は、移動操作とリモート同期の関係を明示的には条件化していない
**推奨される対応:** 移動後・次回同期前の状態を区別できる状態モデル（例: 公開済み/未公開/更新あり の三値）を problem.md の解決条件に追加する

### F-02: 移動（改名）で使われなくなった旧パスの画像は台帳から消えるため、次回の同期評価対象から外れ、リモートに孤児として残り続ける

**戻し先:** /tdd-problem（同一 plan）
**出どころ:** 利用インタビュー（実機確認: push コミット `b925ef9` のツリーに `shiba-inu.jpg` が残存）
**解釈・原因の仮説:** `syncImagePublicationState` は画像台帳のキー集合を起点に評価対象を決めるが、`renameEntry` は移動時に旧キーを台帳から削除してしまうため、旧パスの画像はその後どの同期操作でも一切評価されない。problem.md が挙げる症状「ローカルで削除した画像がリモートに孤児として残り続ける」への対処（参照が失われた画像の除去）は削除の場合はカバーしているが、移動（改名）の場合に同じ症状が再現している
**推奨される対応:** problem.md の解決条件に「移動によって使われなくなった旧パスも、次回の同期操作でリモートから除去される」旨を明記し、後続の /tdd-run で `moveImage` が旧パスを除去対象として認識できるよう（台帳に残す、または移動時点で即時に同期評価する等）修正する

### F-03: 検出外参照宣言の見出し「検出外参照」が語彙用語のままUIに露出し、作成者自身にも意味が伝わらない

**戻し先:** /tdd-run（同一 plan、次サイクル）
**出どころ:** 利用インタビュー
**解釈・原因の仮説:** 今サイクルでチェックボックスの説明文（「参照がなくても非公開にしない」）は改善されたが、`<dt>検出外参照</dt>` という見出し自体は変更されておらず、語彙用語がそのままUIラベルとして露出し続けている。F-02 の利用仮説が想定した「外れ」（語彙上の意味とUI表示が乖離する）がそのまま発生した
**推奨される対応:** ユーザーの具体案（「検出外参照」の見出しをなくし、[公開状態] 配下に「非公開にしない」チェックボックスとして統合する）を次サイクルの設計の出発点とする

### F-04: 画像詳細メタデータ欄の削除ボタンの見た目が他の操作ボタンと不揃い

**戻し先:** /tdd-run（同一 plan、次サイクル）
**出どころ:** 利用インタビュー
**解釈・原因の仮説:** `.image-detail-delete-btn` のスタイルがボタン幅を文言に対して不釣り合いに広く取っている
**推奨される対応:** ボタン幅を文言にフィットさせ、適切なパディングと左寄せに調整する

## 発見（メタ観点: 新tdd-run試走・成層ツリー実験）

このセッションは editor-image-library の問題自体のフィードバックに加えて、新しい tdd-run（`~/dev/tdd-skills/redesign/tdd-run-stratified-tree-experiment.md` の成層ツリー実験）の試走も兼ねていた。以下はそちらの観点の発見で、プランの問題領域ではなくスキル自体への申し送り。

### F-05: 既存システム調査段階で dict-search.js が使われず、直接 dictionary.json を読むスクリプトが構築された

**戻し先:** tdd-skills
**出どころ:** 利用インタビュー（ユーザー報告）
**解釈・原因の仮説:** root（作成者）の定義タイミングでは dict-search.js が活用されていたと見られるため、語彙規範の参照が既存システム調査段階では後回しになっている。調査段階の手順に辞書検索ツールの利用が明示されていない可能性がある
**推奨される対応:** 既存システム調査段階の手順に dict-search.js の利用を明記する

### F-06: 成層ツリーの能力層ノードで分解が甘く、1ノードに複数操作が畳み込まれてテスト基準を作れない例があった

**戻し先:** tdd-skills
**出どころ:** 利用インタビュー（ユーザー報告）
**解釈・原因の仮説:** 「インラインファイル名編集UI は クリックで編集フォームに切り替わり、保存で移動を実行し、取消でもとの表示に戻せる」のように、1文に複数の操作（切り替え・保存・取消）が畳み込まれたノードが生成された。行為層／能力層の区別自体は明確でテストツリーとして分かりやすく、日本語表現も自然（「〜ができる ができる」のような無理な当てはめがない）だったが、能力層内部の「1ノード1能力」への分解基準がルール化されていない
**推奨される対応:** 能力層ノードは「編集ボタンは、クリックしたら編集フォームが表示される」のように単一の操作・単一の検証観点に分解する基準を実験ルールに追加する

### F-07: depgraph-search.js（依存グラフ専用ツール）が使われず、生成済み dependency-graph.json を直接読もうとした

**戻し先:** tdd-skills
**出どころ:** observations.md（2026-08-01 実装中の気づき）・利用インタビューでの再確認
**解釈・原因の仮説:** 辞書検索（F-05）と同型の問題で、専用ツールの利用が手順として徹底されていない
**推奨される対応:** 依存グラフ確認の手順に depgraph-search.js の利用を明記する。dict-search.js の徹底（F-05）と合わせて、専用ツール利用のチェックリスト化を検討する

### F-08: ルート行為記述の単独承認 → 受け入れテスト記述 → テストツリー提示、の3段階が一拍多く感じられた

**戻し先:** tdd-skills
**出どころ:** 利用インタビュー（ユーザー報告）
**解釈・原因の仮説:** V字モデルとして見れば不自然ではなく、現状の運びは妥当という評価だが、ルート承認とテストツリー提示を同時に行っても成立しそうという印象があった
**推奨される対応:** 次回の実験でルート承認とテストツリー提示の統合を試すことを検討する（弱い指摘のため必須の変更ではない）
