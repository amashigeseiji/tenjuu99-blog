## 発見（解釈・原因の仮説、戻し先つき）

### F-01: 移動（改名）操作は台帳の公開済み参照をそのまま引き継ぐため、実体を確認しないまま「公開済み」と表示され続ける

**状態:** 解消（2026-08-02 の利用で再現せず。移動すると「更新あり」になることを確認）
**戻し先:** /tdd-problem（同一 plan）→ problem.md v7 → /tdd-run（US-09）
**出どころ:** 利用インタビュー・成果物レビュー（`packages/editor/server/imageLedger.js` の `renameEntry`、`packages/editor/server/move_image.js`）
**解釈・原因の仮説:** `renameEntry` は台帳エントリ（`publishedReferredBy` を含む）を新しいキーへそのままコピーするだけで、リモートへの実際の反映は行わない。公開状態インジケーターは台帳の値をそのまま表示するため、移動直後は「まだ同期されていない」という状態を区別できない
**推奨される対応:** 移動後・次回同期前の状態を区別できる状態モデルを problem.md の解決条件に追加する
**解決の形:** 二値の #画像公開状態 を表示の役割から降ろし、記事と共通の #公開ステータス（未公開/更新あり/公開済み/リモートのみ）を画像にも適用した。移動は #移動元パス の記録によって「同一エントリの未同期の変更」として読ませる

### F-02: 移動（改名）で使われなくなった旧パスの画像は台帳から消えるため、次回の同期評価対象から外れ、リモートに孤児として残り続ける

**状態:** 解消（2026-08-02 の利用で再現せず。`git log` で旧パスが unpublish コミットとして積まれることを確認）
**戻し先:** /tdd-problem（同一 plan）→ problem.md v7 → /tdd-run（US-10）
**出どころ:** 利用インタビュー（前周の実機確認: push コミット `b925ef9` のツリーに `shiba-inu.jpg` が残存）
**解釈・原因の仮説:** `syncImagePublicationState` は画像台帳のキー集合を起点に評価対象を決めるが、`renameEntry` は移動時に旧キーを台帳から削除してしまうため、旧パスの画像はその後どの同期操作でも一切評価されない
**推奨される対応:** 移動によって使われなくなった旧パスも次回の同期操作でリモートから除去されるようにする
**解決の形:** 画像公開同期器が「公開された画像に #移動元パス があれば、そのパスもリモートから取り除いて記録を消す」規則を持つようにした。GC の評価対象をリモート一覧全体へ広げる案は「疑わしきは消さない」に反するため棄却し、移動由来でないリモート残存は別枠からの手動除去（US-10）に委ねた

### F-03: 検出外参照宣言の見出し「検出外参照」が語彙用語のままUIに露出し、作成者自身にも意味が伝わらない

**推奨される対応:** 「検出外参照」の見出しをなくし、[公開状態] 配下に「非公開にしない」チェックボックスとして統合する

### F-13: インラインファイル名編集は Enter で確定できず、その Enter が記事フォームの「公開する」を走らせうる位置にある

**推奨される対応:** 画像詳細パネル内の入力での Enter の扱いを決める（確定に割り当てる／暗黙送信を止める）。フォーム構造そのものの見直しは範囲が広いため別途判断する

### F-14: 記事のサイドバーは「リモートのみ」のファイルをディレクトリツリーの中に混ぜたまま残っている

**状態:** 未処理
**戻し先:** 新規 plan（エディタのサイドバー）
**出どころ:** observations.md（2026-08-02 分解中の気づき）・利用インタビュー
**解釈・原因の仮説:** `packages/editor/server/get_sidebar.js` は `collectStatuses` が返した `remote-only` のファイルをローカルのファイルと同じツリーに載せている。分解の対話で「サイドバーがディレクトリ型のファイルシステムを模したものである以上、ローカルファイルシステムに無いものをその中に表示するのは直感的理解と離れる」との判断があり、画像ライブラリ側は別枠表示を採ったが、記事サイドバー側は同じ指摘が当てはまる状態のまま残った。**同じエディタの中に二つの流儀が並んでいる**
**推奨される対応:** 記事サイドバーの「リモートのみ」も別枠表示に揃えるかを検討する。あわせて、別枠の可読性がユーザー本人以外に通じるかは未検証である（「これはわたしは理解できますが、ほかのユーザーがどうかはわかりません」）ことも入力にする

### F-16: pnpm の self-dependency（`file:./`）の古いコピーが実装変更を握りつぶす

**状態:** 未処理（据え置き。2026-08-01 の観察メモから項目化した）
**戻し先:** 新規 plan（プロジェクトの開発環境）。または恒久化せず記憶に留める判断もありうる
**出どころ:** observations.md（2026-08-01・2026-08-02 実装中の気づき）
**解釈・原因の仮説:** このプロジェクトは自身を `@tenjuu99/blog` として `file:./` 依存で `node_modules` に持ち、サーバーはHTTP経由の bare specifier 解決を踏む。`node_modules/.pnpm` 配下のコピーが固まり、`pnpm install --force` でも再同期されなかったため、ソース編集が `dist/js/` に反映されず受け入れテストが原因不明のタイムアウトを起こした。シンボリックリンクへの置き換えで解消した。**本プランに限らずプロジェクト全体に影響する**。関連して、`pkill -f "node bin/dev-server"` が同じパターンの他プロセスを巻き込むこと、ポート8000を `npm run server`（ファイル監視なし）が保持しているとソース変更が配信物に反映されないことも観察されている
**推奨される対応:** self-dependency の解決方法をリポジトリの手順として固定するか、開発時のシンボリックリンク構成を既定にする
