# Observations: gitless-publication-means

**日時:** 2026-08-16（合成は 2026-08-15 開始）

## 実装中の気づき

### ツリー・語彙の変更

- ノードの改名（構造は不変、ユーザー指示）: 「内容指紋」→「フィンガープリント」（en `Fingerprint`、`lib/publishing/fingerprint.js`）、「資格情報」→「認証情報」（en `Credential` は据え置き）。problem.md には「資格情報」の語が残っている（入口文書は tdd-run で書き換えない）
- ノードの述語を一語補った（ユーザー承認済み）: 「GitHub公開手段 はリモートが進んでいたら反映を拒み…」→「**反映しようとするファイルについて**リモートが進んでいたら反映を拒み…」。実アプリはエンドポイント呼び出しごとに手段を組み立て直し、その時点のリモートの現在の版を読むため、「知っている版よりリモートが進んでいる」という git 手段の粗い判定は実質的に起きなかった。判定の拠り所を同期の基点（ファイル単位）に置き換え、「そのファイルについて、リモートの内容が手元とも基点とも違う」なら何も書かずに拒む形にした。別ファイルの公開が先にあっても自分の公開は通る（上書きは起きず、次の取り込みで届く）
- 語彙 5 件を solution として登録: GitHub公開手段・GitHub接続・フィンガープリント・認証情報提供者・公開手段解決器（redefine、relations のみ）。認証情報提供者は手段に中立に定義した（FTP 等が来ても同じ形。実装は GitHub 分だけ）

### 局所修繕（ツリーの形は不変）

- 「同期の基点を進められる」に隠れた子（it）を追加: **初回接触の基点揃え**。基点の記録がまったく無いコンテンツルート（clone 済み相当のフォルダを初めて開いた）では、組み立て時にリモートと同じ内容のファイルすべての基点を揃える。以降は読み（diffFromRemote / lineageOf）で「同じ」と分かった時点で個別に揃える。これが無いと、手元で編集しただけで「両側で変わった」に退化する（利用仮説の「外れ」条件）
- 「取り除け、手元には触れない」に it を追加: コンテンツルート内の**絶対パス**でも受け付ける。`remove_remote_image` エンドポイントは `lib/dir.js` の絶対 `srcDir` から絶対パスを組み立てて `means.remove` に渡しており、git 手段は git がリポジトリ内の絶対パスを受け付けるので通っていた。GitHub 手段では相対パスに正規化しないとリモート上のパスと突き合わせられず、「取り除きました」と言いながら何も除去しない（受け入れテスト US-01 S6 で発覚）

### 置き場所・構成の決定（合成で決める事項）

- 同期の基点: `<コンテンツルート>/.blog/sync-base.json`（パス → フィンガープリント。`.cache/` と違い消してはいけない）
- 認証情報: `<コンテンツルート>/.blog/credentials.json`、`{"github":{"token":"..."}}` と手段名で区切る
- 構成: `blog.json` の `publish: { "means": "github", "github": { "owner", "repo", "branch", "api_base"? } }`。解決器は `resolvePublicationMeans({ cwd, ...config.publish })` で構成一式を受け取る形に変えた（呼び出し側 9 箇所を揃えた）
- `.gitignore` に `.blog/` を追加（このリポジトリ）。利用者側のリポジトリでも同様に要る（docs/spec.md に記載）

### 詰まったポイント

- `dict-search.js` の `<plans_dir>` は `./` または絶対パスで始まらないとプロジェクト辞書として扱われない（`plans/xxx` は検索語扱い）。序盤の検索で plans 側のエントリが見えていなかった
- `node --test tests/publishing/*.test.js` を並列で回すと `.cache/` へのコピー競合（EEXIST）で既存テスト `publicationMeans.test.js` が落ちる。`npm test` は `--test-concurrency=1` なので影響なし。既存のテスト分離の問題で本プランの変更ではない
- 依存グラフ（`.claude/tdd/dependency-graph.json`）は `@tenjuu99/blog/lib/...` の自己参照 import を辺として解決しないため、`packages/editor/server` → `lib/publishing` の到達性が見えず、孤立ノード検査は結論不能（既存の git 手段でも同じ）。実到達性は e2e と受け入れテストで確認した

### スキルの使い方で想定と違ったこと

- 「緑になったら確認を求める」（手順3）の直後に組み込みで意味的な問題（拒否が起きない）が見つかり、ツリー文言の判断を仰ぐ往復が入った。組み込みの e2e を手順3の確認より前に一部回しておくと、確認を一度で済ませられたかもしれない
- 受け入れテストでは「git の無い環境」を PATH から git を外して起動したサーバーで表現した（`bin-without-git/` に node だけを置く）。「git がインストールされていない」という Given を機械的に検証できる

### 実装しなかったこと・限界

- 初回接触より前にリモートが進んでいたファイルは基点が無く、分岐扱い（正直な退化）。初回セットアップ（範囲外）が基点を書けば解消する
- 「リモートで消されたものの伝播」は設計判断どおり埋めていない（`judge` は remote null → localOnly）。基点があるので検出は可能
- 認証情報の獲得・配置 UI は後続プラン。当面は `.blog/credentials.json` を手で置く
- 手段はエンドポイント呼び出しごとに組み立て直し、そのたびに GitHub API を 3 回（ref / commit / tree）呼ぶ。サイドバーや画像ライブラリの読みが頻繁だと API の回数が積み上がる（認証済みで 5000 回/時）。プロセス内キャッシュは入れていない

## ブラインドレビュー（review.md）への対応

- 即時対応した: R1（同期の基点を毎回置き場所から同期的に読み直す — 単一プロセス内で交錯しない）、R2（除去にもファイル単位の「リモートが進んでいる」検査を適用、it 追加）、R3（publish/unpublish の unknown 文言を手段中立に）、R4（403 の rate limit / 429 を `rateLimited` として区別、`notFound` の it 追加）、R5（相対の `..` も拒む）、可読性（宣言順の整理・`known`→`currentVersion`・二段の検出の説明・remoteState の副作用の説明）、重複 5-1/5-2（文言と `BLOB_MODE` を定数に）
- 持ち越し（feedback で差し戻し先を判断）: 基点を失ったファイルの UI 上の脱出路（分岐の解消は sync-diff-preview の範囲）／リクエストごとの API 回数（プロセス内キャッシュ）／`judge` と `createGitLineageOf` の判定規則の重複（git 手段の書き換えは再節合）／editor 9 ハンドラの `{ ...config.publish, cwd: rootDir }` の同型（editor 側の診断）
- 対応不要: R6（初回接触の N 回書き込みは一度きり）、テスト内の接続セットアップの繰り返し（注入部品を明示する意図）
