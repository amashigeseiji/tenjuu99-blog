# テストツリー: gitless-publication-means

## GitHub 経由の git 非依存公開手段（2026-08-15・新規型）

### できるのツリー

```
作成者 は手元に git が無くても、記事と参照画像の同期操作の一式を、git 運用と同じリモートに対して行える [publishing]
├── 作成者 は git の無い環境で、記事と参照画像を公開・更新・非公開にできる [publishing]
│   ├── GitHub公開手段 は記事と画像（バイナリを含む）を一度の反映でまとめてリモートに届けられる [publishing]
│   ├── GitHub公開手段 は反映しようとするファイルについてリモートが進んでいたら反映を拒み、先に取り込みが要ることを伝えられる [publishing]
│   ├── GitHub公開手段 は git 運用の反映と見分けのつかない形（履歴が一本につながり、内容が同じ）でリモートを更新できる [publishing]
│   ├── GitHub公開手段 はリモートからファイルを取り除け、手元の原稿には触れない [publishing]
│   ├── GitHub公開手段 は反映・除去・取り込みが済んだファイルの同期の基点を進められる（除去なら消す）[publishing] ★共有
│   └── GitHub接続 は認証情報を添えて、リモートの現在の版とそこに含まれるファイル一覧・内容を読め、新しい版を書き込める [publishing] ★共有
│       ├── GitHub接続 は届かないとき（認証情報が無い・通らない・不通）に沈黙せず誤りを返せる [publishing]
│       └── 認証情報 は手元だけの置き場所から読み出せ、無ければ無いと分かる [publishing]
├── 作成者 は git の無い環境で、記事と画像の公開ステータスを git 手段と同じ意味で読める [publishing]
│   ├── GitHub公開手段 はリモートのファイル一覧・存在・手元との差分の有無を示せる [publishing]
│   │   └── フィンガープリント は手元のファイル内容（テキスト・バイナリ）から、リモート側の同じ内容の識別と一致する指紋を計算できる [publishing]
│   └── GitHub公開手段 はリモートの知識を最新にできる [publishing]
├── 作成者 は git の無い環境で、執筆内容を失わずにリモートの記事と画像を取り込める [publishing]
│   ├── GitHub公開手段 はリモートの内容（バイナリを含む）を手元に書き出せる [publishing]
│   ├── GitHub公開手段 は同期の基点を用いてファイルごとの版の連なりを示せる [publishing]
│   │   ├── 版の連なり は手元・リモート・基点の三者の内容の同異から、先行・後行・分岐・手元に無い事情（消された・他所で作られた）を判定できる [publishing]
│   │   └── 同期の基点 はファイルごとの「揃えた時点の内容」の記録を進め・消し・参照でき、コンテンツルートごとにプロセスをまたいで保てる [publishing]
│   └── （★共有: 同期の基点を進める／GitHub接続）
└── 作成者 は構成で手段を選ぶだけで、git 運用のマシンと同じリモートを共有でき、既存の git 運用は今までどおり続けられる [publishing]
    └── 公開手段解決器 は構成に指定された手段（GitHub）を、リモートの識別と認証情報の提供者を与えて組み立てられる [publishing]
```

**Entry point:** `packages/editor/server/{publish,unpublish,pull,get_sidebar,get_image_library,…}.js`（既存エンドポイント、変更なし）→ `lib/publishing/publicationMeansResolver.js` の手段登録に GitHub 手段が加わる → 作成者の同期操作

**セミラティス（共有ノード）:**
- 「同期の基点を進められる」— 届ける向き（反映・除去）と取り込む向きの両方から使われる
- 「GitHub接続」— GitHub公開手段のすべての読み書きが通る口

### 設計上の判断（problem.md の開いている点への回答）

1. **手段の選択**: blog.json の `publish.means`（共有）で一つに決める（手段はリモートの属性）。GitHub 手段のリモート識別（所有者・リポジトリ・ブランチ）も blog.json 側。マシンごとに手元に残るのは認証情報だけ
2. **基点の保管と粒度**: ファイル単位。GitHub公開手段の内部知識として持ち、git 手段は変更しない（環境から借り続ける）。置き場所はコンテンツルート内の非公開の場所で、具体名は合成で決める
3. **リモート側で消されたものの伝播**: 本問題では埋めない。git 手段と同じ読み（手元にあってリモートに無い＝localOnly）に揃えて退行させない。基点を持つことで検出可能になる事実は申し送りに残す
4. **削除する**: 非公開のあとの手元の操作で手段に依存しない（既存どおり）。ツリーに独立ノードは置かない
5. **接続の分離**: GitHub接続を薄い口として切ることで、手段の論理（基点・指紋・連なり・一括反映）は接続に依存せずインメモリでテストでき、「第二の手段が抽象に要求するもの」が接続以外の部分として言葉になる（後続の他ホスト対応の出発点）
6. **認証情報の扱い**: 獲得・配置（トークン発行の案内・入力 UI・保存・期限つきトークンの更新）は**後続プラン**。本プランは読み側の契約——手元だけの置き場所・形式・無いときの挙動——を決めて申し送る。当面は作者が手作業でトークンを置く暫定運用。GitHub の認証方式（PAT / OAuth / GitHub App）は消費側では「トークンを添える」に収束するので接続・手段の作りは変わらないが、期限つき・更新ありの方式では認証情報の形が「静的な値」から「更新される組」に変わりうる。その差が接続や手段に波及しないよう、**接続には認証情報そのものではなく「いま有効な認証情報を返す提供者」を渡す**。本プランでの提供者は「手元だけの置き場所から静的な値を読むだけ」
7. **sync-diff-preview との順序**: 本問題を先に解く（基点の知識があちらの材料になる）

### 整形式チェックの注記

- 述語中の「git」は避けたい環境装備そのものを指す要件レベルの事実（何が無くても・何と同じ）であり、実装手段の漏れではないので残す。「GitHub」は主語（概念名）にのみ現れ、述語に API・SHA・commit・HTTP 等の技術語は置かない
- loadability: GitHub接続は通信関数を注入可能に、同期の基点・認証情報は置き場所を注入可能にする前提で、すべてテスト環境でロード可能
- lint スクリプトは無いため目視

### 利用仮説

**使ったらこうなるはず:**
- （届ける）作者が git を使わない設定の環境から、画像付き記事の公開・更新・非公開をエディタだけで完了でき、サイトの配信が従来どおり起きる。別マシンの公開で先を越されていたら反映が拒まれ、「先に取り込み」が伝わる（US-01 S1・S2・S5、US-04 S1〜S3）
- （読む）サイドバーと画像ライブラリのステータス（公開済み・更新あり・リモートのみ・未公開）が、git 運用のマシンで見たときと同じ読みになる（US-01 S6）
- （取り込む）別マシンの画像付き記事が手元に現れてプレビューされる。両側で変わった記事は守られて理由が出る。手元で編集しただけの記事は見送りにならず次の公開で反映される。削除した記事は復活しない（US-01 S4・S7、US-03）
- （混在・退行なし）マシン A（git）と B（GitHub 手段）が互いの公開を取り込める。A の git 運用は今までどおり（US-02）

**こうなったら外れ:**
- 取り込みで執筆内容が消える／画像だけ・記事だけが届く中途半端な状態になる
- ステータスの読みが手段によって食い違う
- 認証情報が blog.json やリモートに載る
- 既存の git 運用が退行する／UI に commit・push・SHA 等の言葉が出る
- 同期の基点が失われ、手元で編集しただけで毎回「両側で変わった」になる
