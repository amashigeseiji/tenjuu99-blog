# Findings: gitless-publication-means

**日時:** 2026-08-16
**対象:** plans/gitless-publication-means/

## 操作の事実

環境: コンテンツルートは既存の原稿フォルダのコピー（`.git` 無し、以下「git 無しフォルダ」）。リモートは GitHub に新規作成した空リポジトリ。`blog.json` に `publish.means: "github"` と `github.owner/repo` を設定し、`.blog/credentials.json` を手で配置。`npm run server` で起動しエディタから操作。

1. 空リポジトリへの最初の「公開する」→ サーバーログに `GitHubConnectionError: GitHub がエラーを返しました（409）: Git Repository is empty.`。UI ではなくターミナルのログで確認
2. GitHub 上で README.md を追加してから再度「公開する」→ `.git` 無しの手元からコミットが積まれた
3. GitHub Pages（Actions）でビルドするには package.json / package-lock.json / blog.json / src/templates / src/css / src/helper 等の資材がリモートに要り、エディタからは届けられない。GitHub から clone した別フォルダ（以下「git 有りフォルダ」）を作り、そこから git で資材をコミットして準備した
4. 準備後、「公開する」でリモートが更新され、サイトが GitHub Pages で配信された。記事の更新（再公開）・非公開も期待どおり。コミットメッセージは `publish` / `unpublish`
5. 画像を参照する記事の公開: 画像もコミットに含まれた（期待どおり）。Pages には表示されなかった（作者の見立てはビルド側の欠陥。コミットは積まれていたので公開の行為には帰属させない）
6. 画像を参照する記事の非公開: 記事の除去と画像の除去が**別々のコミット**として積まれた（Actions が二度走る）
7. サイドバーの公開ステータスは git 手段のときと同じ表示で、内容が理解できる
8. 拒否: GitHub 上で同一記事を編集してリモートを進めた → 手元のサイドバーは「更新あり」。その状態で手元を編集して「公開する」→ 画面下部に「公開失敗: リモートが先に進んでいます。先に取り込んでから、もう一度公開してください」。「公開する」ボタンは押せる状態だった
9. 取り込み: 8 の状態で「リモートから取り込む」→ 「新しく取り込むものはありませんでした ／ 見送り: yarigatake.md — 手元とリモートの両方で変わっているため、手元の内容を守って取り込みを見送りました」。手元をリモート差分前の内容に戻してから取り込むと成功した
10. 未試行: 削除（手段非依存のため取り下げ）、git 運用マシン側での GitHub 手段の公開の取り込み（US-02 S2）、両側で変わった以外の取り込み保全（US-03 S2・S3）

## 利用仮説の照合

| 利用仮説 | 実際 |
|---|---|
| （届ける）git を使わない環境から画像付き記事の公開・更新・非公開が完了し、配信が従来どおり起きる。先を越されていたら拒まれ「先に取り込み」が伝わる | 期待側（公開・更新・非公開・拒否の文言はすべて起きた）。ただし「届ける」に至る前の準備が主要な問題だった（下記） |
| （読む）ステータスの読みが git 運用と同じ | 期待側 |
| （取り込む）別マシンの記事が手元に現れる。両側で変わった記事は守られて理由が出る | 期待側（GitHub 上の編集を別マシン相当として）。ただし守られたあとの脱出路が無い |
| （混在・退行なし）互いの公開を取り込める。git 運用は今までどおり | どちらとも言えない（git 側での取り込みは未試行。資材投入は git で問題なくできた） |
| 外れ条件（執筆内容が消える／片方だけ届く／認証情報が blog.json やリモートに載る／UI に commit・SHA が出る／基点が失われる） | いずれも起きていない |

**利用仮説そのものの評価:** 仮説は「混在」「取り込み」「別マシン」に重心があり、作者の主要ユースケース「git の無いコンピュータで運用を始められるか」を測っていなかった。測る相手が違った。

## 印象（ユーザーの言葉）

- 「利用仮説との照合が、自分が欲しいと思っているユースケースに対してちょっとズレている。git と GitHub の相互運用性は要件として必要ではあるものの、そこをそんなに求めていたわけではない。複数台の利用想定も、構造的に必要なものではあるが、主要ユースケースでもない」
- 「主要ユースケースとして想定しているのは、コンピュータに git が無い場合に運用できるか。そのための手続きとしてリモートで資材のビルドをするための諸々の設定が必要で、それを準備することが、作業としては全部重い。自分がこのレポジトリの特性を知っているからできているだけで（それでも困難）、知らない人はまずなにもできない。クレデンシャルの用意も Claude に聞かなければわからなかった」
- 「準備ができてからのソフトウェアの動作としては、期待どおりで、git のほぼ完全な代替になっている」
- 「（problem 作成時に）『認証のほうが先のほうがよくないですか？』というやりとりがあり、初期セットアップをどうするのかがまったく想像ついていなかったから、そのユースケースを先に正確に手順化しておきたいというのがなんとなくあった。公開・非公開・削除などのユースケースは従来からあるもので『従来通りに動くことが期待される』というだけだが、初期セットアップはまったく新しい領域で、ここのユースケース・手順の明確化はやはり先にやるべきだった」
- 「github api をつうじて公開・非公開などの処理ができることはユースケースを増やすことではなく、従来のユースケースがそのまま維持されているということであり、その一方で、公開手段を選択することができるというのが新しいユースケースです。それが実現されていないので、問題のたてかたがやはりよくなかった」
- 非公開の二重コミットについて「github actions を main にフックしている場合どちらでも動いてしまうので、これは良い状態ではない」
- 「更新あり」について「ローカルが進んでいるように見えた。『更新あり』の意味はローカル更新ありのみに限定し、リモート更新ありは『リモート更新あり』にしないと意味が伝わらない」
- 拒否について「公開できないことがわかっているのに『公開する』が押せるようになっている。確定しているのであれば非活性にしたほうがよい」
- 分岐について「リモートに差分があったとき、ユーザーは対処のやりようがほぼない。git ログを読んで対処する以外にないのは問題がある。ローカルの差分を除去してリモート優先にする、みたいな処理があったほうがいい」

## 発見（解釈・原因の仮説、戻し先つき）

### F-01: 新しいユースケースは「公開手段を選択できる」であり、問題定義はそれを測っていなかった
**状態:** 対応済み（/tdd-problem, 2026-08-16 — v3 ではなく分割。plans/publication-means-selection/problem.md v1（手段の選択と認証情報の用意）を新設。既存ブログの始め方（clone 相当）・新規ブログの始め方（資材一式の生成）は別 problem として後続。本 plan は同日の /tdd-feedback 再開でクローズ判断を B → A（アーカイブ）に変更）
**戻し先:** /tdd-problem（当初は同一 plan の再定義 v3 — 2026-08-16 の対話で三分割に変更）
**出どころ:** 利用インタビュー
**解釈・原因の仮説:** ツリーの root「作成者は手元に git が無くても同期操作の一式を行える」と利用仮説は、既存ユースケース（公開・非公開・取り込み）が手段を替えても維持されることを測っていた。それは達成された。しかし作者にとって新しい行為は「公開手段を選択できる」ことであり、その成立にはリモートの初期化（空リポジトリに届く）、サイトの資材をリモートに置くこと、認証情報の配置、という準備が含まれる。problem.md v2 はこれらを「初回セットアップ・範囲外」に切り出したが、範囲外にした部分こそが主要ユースケースの成否を決めていた。problem 作成時に「認証を先にすべきでは」という作者の直感があり、Claude の「セットアップ後の処理を先に」という提案でこの順になった経緯がある。
**推奨される対応:** 問題を「作成者が公開手段を選択でき、選んだ手段で運用を始められる」として立て直す。手順化（作者自身が手動でテストできる手順）を先に置く。空リポジトリの 409、資材の配置、認証情報の獲得・配置は同じ問題の内側。今回の GitHub 手段の実装は、その問題に対する既存資産として使う。

### F-04: サイトの資材（ビルドに必要なファイル）が手段から届けられない
**状態:** 未処理
**戻し先:** /tdd-problem（新規 problem gitless-new-blog-onboarding（未作成）で扱う。「公開する＝ソースのままコミットを積む」がリモート側のビルド・デプロイを暗黙に前提していることの明示化もここ — 2026-08-16 の分割による）

### F-05: 非公開で記事の除去と画像の除去が別々の反映になる
**状態:** 未処理
**戻し先:** /tdd-refactor（診断の依頼）
**出どころ:** 利用インタビュー
**解釈・原因の仮説:** unpublish ハンドラは記事の除去（`unpublish`）と 画像公開同期器 による画像の除去を順に呼び、`means.remove` が二回走る。git 手段でも一回ごとに commit + push するので同じく二コミットになる（既存挙動、手段非依存）。公開側は 公開対象コレクター が記事＋画像を一度の反映にまとめるのに対し、非公開側は除去の単位が 公開対象 になっていない非対称。

### F-06: 「更新あり」がリモート側の進みを区別しない
**状態:** 未処理
**戻し先:** /tdd-problem（別プラン sync-diff-preview の problem.md 改版の材料）
**出どころ:** 利用インタビュー
**解釈・原因の仮説:** 公開ステータス は手元とリモートの内容差分の有無だけで「更新あり」を決め、向きを持たない（git 手段でも同じ、既存挙動）。GitHub 手段でリモートを進めて初めて、この読みが向きを持たないことが見えた。版の連なり（先行・後行・分岐）は手段が持っているが、ステータスに反映されていない。
**推奨される対応:** sync-diff-preview の「実行前に噛み合わないことを察知できる」に含める。「更新あり」を手元側の変更に限定し、リモート側は別の読み（「リモート更新あり」）にする案は作者の言葉として渡す。

### F-08: 分岐したときの脱出路が無い
**状態:** 未処理
**戻し先:** /tdd-problem（sync-diff-preview の材料。observations の持ち越し「基点を失ったファイルの UI 上の脱出路」もここに合流）
**出どころ:** 利用インタビュー / observations.md
**解釈・原因の仮説:** 取り込みは執筆内容を守って見送るが、その先（リモートを優先して手元差分を放棄する、内容を見比べる）が無い。手元を手で戻す以外に方法が無く、git ログを読める人しか対処できない。sync-diff-preview の「リモートを優先して手元の差分を放棄する選択ができる」そのもの。
**推奨される対応:** sync-diff-preview へ。「拒まれる」という仕様自体が分岐の解消の仕組み次第で変わりうるため、拒否（US-04 S2）と見送り（US-03 S1）の行為はこの周では登記しない。

### F-09: 行為の登記の枠 — 手段が替わっても行為は同じ

**出どころ:** 成果物レビュー
**解釈・原因の仮説:** 「手元に git が無くても記事を公開できる」等 5 件を登記候補にしたところ、防衛線が act-0009（非公開に戻せる）・act-0021（取り込める）との近接で停止した。作者の判断は「これらは新しい行為ではなく既存の行為が別手段でも維持されただけ。claim に『git が無くても』と書くと任意の手段と読め、検証内容も特定できない」。一度書いた 3 件（act-0023〜0025）は同じ枠の誤りだったので git で取り消した。台帳に必要なのは「既存の行為に新しい手段の witness を足す」操作であり、行為を手段ごとに複製することではない。

### F-13: problem 段階で「新しく成立する行為」を問うチェックが無い
**状態:** 未処理
**戻し先:** tdd-skills（/tdd-problem・/tdd-run の手順）
**出どころ:** 利用インタビュー（クローズ後の対話）
**解釈・原因の仮説:** problem → run の流れは「…できない」を「…できる」にする前提で、行為（ユースケース）が増えることを暗黙に仮定している。今回は増えなかった。GitHub 経由の公開・非公開・取り込みは台帳の act-0008／0009／0021 の**成立条件（手段）が広がっただけ**で新しい行為ではなく、本当に新しい行為「作成者は公開手段を選択できる／選んだ手段で運用を始められる」は範囲外に置かれた。problem 段階で台帳を引いて「この問題で新しく成立する行為は何か」を問う形が無かったため、(1) 既存行為の維持に受け入れシナリオ 16 本を新規に書き、利用仮説の照準も維持側（混在・取り込み）に寄った、(2) 作者の「認証が先では」という直感（新しい行為の所在を指していた）が問いの形を持たず消えた、の二つが起きた。F-09（既存 act に witness を足す操作が無い）はこの下流の症状。ツリーの装置層（基点・指紋・接続）と単体テストは手段追加に要るもので無駄ではない。無駄だったのは受け入れ層の重複と仮説の照準。
**推奨される対応:** /tdd-problem の「解決したと言える状態」に必須項目「この問題で新しく成立する行為（`<actor> は … できる`）。無ければ『無し』と明記し、成立条件が広がる既存の行為を台帳 id で挙げる」を加える（書く際に acts-search.js で照合する）。/tdd-run はこの欄で分岐する — 新しい行為あり: ツリーの root はその行為、受け入れはその分だけ新規／無し（維持型）: ツリーは装置層中心、受け入れは既存 spec を手段でパラメータ化して既存 act に witness を足す、利用仮説は「退行なし＋新手段で同じ読み」の形。両方ある問題（今回）は二つのプランに分ける判断材料になる。最終判断は表＋承認で作者が持つ。
