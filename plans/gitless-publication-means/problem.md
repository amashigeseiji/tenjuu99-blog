## 問題

公開手段の抽象（`公開手段`・`公開手段解決器`）は確立されたが、実現は `git公開手段` の一つだけである。そしてこの実現は、実行環境の装備——git バイナリのインストール、clone 済みのリポジトリ、認証の設定——に依存している。アプリを配布された人や、ローカルに git を持てない環境（iPad 等）では、公開・非公開・削除・取り込みという同期操作の一式がまるごと使えない。

より深いところに、この依存の本質がある。同期の正しさ——取り込みが執筆内容を上書きしないこと、「手元に無い」の曖昧性（消したのか、他所で作られたのか）の解消——は「共通の祖先の知識」（版の連なり）に立脚しており、現状この知識の出どころは git の履歴である。つまり現行の手段は、同期に必要な知識を**実行環境から借りて**成立している。環境から git を外すということは、この知識の供給源が消えるということであり、借りていた知識をシステム自身がどう持つかが本問題の中心にある。

### やりたいこと

- **git の無い環境で同期操作の一式が使える**: git がインストールされていない環境でも、公開・更新・非公開・削除・取り込みが実行できる
- **将来の環境の広がりに道を作る**: ローカルに git を持てない環境（iOS/iPadOS 等）へ広げる余地を作る
- **git 運用との共存**: 既存の git 手段は残し、並立する第二の手段とする。同じリモートに対して git 手段のマシンと新手段のマシンが混在できる（マシンAで git 公開した記事を、マシンBの新手段で取り込める）

### 障害・制約

- **現行の唯一の実現が環境装備に依存**: `git公開手段` は git CLI の呼び出しで実現されている。git が無い環境では、リモート状態の参照・反映・除去・取り込み・版の連なりの参照のすべてが失敗する
- **同期の正しさが git の履歴に暗黙依存**: 版の連なり（先行・後行・分岐・不在の曖昧性の解消）は履歴と共通の祖先の知識があって初めて言える。手段の抽象は「知識を持たない場合は diverged に正直に退化」を許すが、退化した手段では取り込みが実用にならない——手元で編集しただけで「両側で変わった」と判定され、見送りが頻発する。sync-operations の申し送りにあった向きの担保の選択肢のうち、(a)「手段に要求する（git は自然に満たす）」が使えなくなる状況であり、(b)「システム自身が版の連なりの知識を保持する」への移行が避けられない
- **リモートは同じものを指し続ける**: リモートの実体は引き続き GitHub 上の git リポジトリであり、デプロイ（CI/CD）もそこに紐づく。新手段は「git の運用が作るリモート」と読み書き両面で互換でなければならず、リモートの形式を新手段の都合で変えることはできない
- **資格情報の置き場所**: git は認証を環境（credential helper）から得ていた。環境に頼らない手段は、リモートへ届く資格情報を自身の建て付けの中で扱う必要がある（資格情報の獲得フローは範囲外だが、必要性は制約として残る）

### 観察された症状

- native app の配布を受けた人が公開・同期をするには、アプリの外で git のインストール・clone・認証設定という手作業が要る。配布物が自己完結しない
- コンテンツルート選択フローには「選ばれるフォルダは事前に clone 済み」という暗黙の前提があり、git を知らない人には満たせない

## 範囲外

- **初回セットアップ**: 空のフォルダにリモートの内容でコンテンツルートを実体化すること、および資格情報の獲得（認証フロー・UI）。別問題として立てる。本問題は「clone 済み相当のフォルダが既にある」ところから始まる
- **GitHub 以外のホスティング**（GitLab 等）: リモートの実体は現運用の GitHub のまま
- **編集セッション・複数人共有**: sync-operations と同じ扱い。1人が複数台を順に使う範囲を対象とする

## 解決したと言える状態（問題領域の言葉で）

- git がインストールされていない環境で、同期操作の一式（公開・更新・非公開・削除・取り込み）が実行できる
- 同じリモートを git 手段のマシンと新手段のマシンが共有しても、互いの成果を壊さない。一方の公開・削除を他方が取り込める
- 取り込み・削除の伝播によって、執筆した内容が失われない（sync-operations の達成水準を新手段でも満たす）
- 既存の git 手段での公開運用が壊れていない（退行しない）
- 公開手段の抽象の意味（公開する・公開ステータス・版の連なり）が、手段の追加によって変質しない

## 技術的背景（調査結果）

- 公開手段の抽象（`PublicationMeans`: remoteState / reflect / remove / takeFromRemote / lineageOf / refreshRemote / deliverable）は手段非依存に定義済みで、取り込みの骨組み（`pull()`）も手段非依存。第二の手段はこの形を満たせばよい建て付けになっている
- **GitHub REST API での実現可能性は対話で概ね確認済み**: リモートの一覧・参照は Git Trees / Blobs API、反映・除去は Git Data API（blob → tree → commit → ref 更新）で対応でき、ref 更新の fast-forward 制約により「リモートが進んでいたら反映を拒否する」分岐の検出と原子性は保たれる。git の blob SHA はローカル計算できるため、差分判定に git は要らない
- **唯一環境から得られなくなるのは「前回同期した時点」の知識**: git では refs（merge-base）が自動で担っていた。システム自身が保持する場合、コミット単位ではなくファイル単位で持てば、部分的な取り込みでも判定が壊れない（コミット単位で持つと、取り込まなかったファイルの判定が反転し、次の公開でリモートの新しい内容を上書きしうる）——という粒度の論点が対話で特定されている
- この知識を自前で持つと、git 版で二相だった取り込み（履歴ごと進める / ファイルだけ取り出す）が一相に単純化し、初回セットアップ（clone 相当）も「空フォルダへの取り込み」に退化して日常の取り込みと同じ経路になる見通し（初回セットアップ自体は範囲外だが、別問題を立てるときの足がかり）
- ローカルに履歴が無くなることで、git が副次的に与えていた「手元の原稿の過去の版に戻る」という保険は新手段には無い。本問題の解決条件には含めないが、利用フェーズで顕在化しうる

## /tdd-run への申し送り

- **語彙定義の種**: 同期の基点（前回同期した時点の知識。手段が環境から借りるのではなく、システム自身が保持するもの）。基点を進める規律（公開の成功時・取り込み時に進める——git では refs が自動で守っていた不変条件の明示化）。資格情報（手段がリモートへ届くために持つもの）
- **開いている点（基点の保管と粒度）**: 基点をどこに・どの粒度で永続化するか。ファイル単位で持つ必要性は調査で特定済みだが、コンテンツルートごとの状態としての置き場所（`.git` が果たしていた役割の後継）は solution domain で決める
- **開いている点（手段の選択）**: 利用者がどの手段を使うかをどう決めるか。既存の `公開手段解決器` は設定（blog.json）由来だが、混在運用（同じ原稿フォルダを git 有り環境と無し環境で使う）まで許すかは未確定
- **開いている点（リモート側で消されたものの伝播）**: 取り込みの候補がリモートの一覧由来である限り、リモートで削除されたファイルは手元に残る。現行 git 手段にも同型の空白があり（版の連なりに「リモートで消された」が無い）、退行ではないが、基点を自前で持つとこの検出が可能になる。本問題で埋めるかは solution domain で判断
- **別問題の種（初回セットアップ）**: 空フォルダからの実体化と資格情報の獲得。コンテンツルート選択フローの `blogJsonNotFound` に第三の継続（リモートから作る）が生えうる、という観察を対話で得ている
- **利用検証の基準**: 作者自身が git の無い（または使わない）環境で実利用できるか。混在運用はマシン2台での実運用で検証できる
