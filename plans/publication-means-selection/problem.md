## 問題

`git公開手段` と並ぶ第二の実現 `GitHub公開手段` は動いており、選んで認証情報を用意しさえすれば、手元に git が無くても公開・非公開・削除・取り込みが git のときと同じ意味で行える。しかし「選ぶ」と「用意する」がアプリの中に無い。手段は共有設定ファイル `blog.json` の `publish.means` を手で編集して選び、認証情報はコンテンツルート内の `.blog/credentials.json` というファイルを手で置く。どちらも、そのファイルの存在と形式を知っている人にしかできず、作者自身でさえ Claude に聞かなければ辿り着けなかった。

つまり、このシステムには「git 無しでも GitHub 経由でサイト運用ができる」という能力が備わっているのに、利用者はその能力があること自体を知りようがない。手段を選ぶという行為がアプリの中に無いために、選択肢が存在することも見えないのである。本問題は、公開手段を選ぶことと、選んだ手段がリモートへ届くための認証情報を用意することを、アプリの外の知識に頼らない作成者自身の行為にする。

本来の用途は native app（配布を受けた、このリポジトリを知らない人）であり、`npm run server` をターミナルで実行できている人は想定利用者ではない（その人は git も node もあり、GitHub 経由を選ぶ理由が薄い）。ただし native app は web のエディタを表示するシェルなので、エディタの中に作れば native app にも載る。検証の簡便さからも、本問題の入口はエディタの中とする。

### やりたいこと

- **公開手段を選べる**: 作成者が、設定ファイルの存在・形式を知らずに、アプリの中で公開手段（git 手段／GitHub 手段）を選び、選んだ手段に要るもの（GitHub 手段ならリモートの識別＝所有者・リポジトリ・ブランチ）を与えられる。選ぶ操作を通じて「この手段なら git 無しで運用できる」ことが分かる
- **認証情報を用意できる**: 作成者が、アプリの中で認証情報（GitHub 手段ならトークン）を登録・差し替えできる。トークンの発行そのものは GitHub 側の操作だが、どこで何を発行すればよいかの案内はアプリの中にある。用意した認証情報は従来どおり手元だけに置かれる
- **選んで用意すれば運用が始まる**: 手元に原稿フォルダがあり、リモートに資材一式（ビルド・デプロイに要るもの）が既にある状態から、選択と用意を終えれば、既存の同期操作の一式が選んだ手段でそのまま動く
- **native app への搭載と互換**: web のエディタに作り、native app にそのまま載る形にする

### 障害・制約

- **選ぶ場所が無い**: 手段は `blog.json` の `publish.means` で決まり、これを書き換える経路はファイルの手編集しかない。選択肢が存在することは spec を読まないと分からない
- **用意する場所が無い**: `認証情報` の現行定義は「獲得のフロー（認証 UI）は範囲外で、用意されているところから始まる」であり、`認証情報提供者` は手元の置き場所から静的な値を読むだけ。置き場所と形式（手段名で区切った JSON）は spec にしか書かれていない
- **認証情報は手元だけに置く、という保証を崩せない**: 認証情報はコンテンツルートごと・マシンごとに手元だけに置かれ、共有設定（blog.json）にもリモートにも含めない。アプリの中で用意できるようにしても、この保証は保たれなければならない（画面に出したものが公開物やリモートに紛れ込まない・画面に平文で残り続けない）
- **手段の選択は共有設定に置かれている**: 手段は「リモートの属性」として blog.json（共有される・リモートにも届く設定）で決まる一方、「git があるか」はマシンの性質である。作成者がアプリの中で手段を選ぶことが、同じリモートを共有する別のマシンの運用に影響しうる（v2 gitless-publication-means から持ち越しの開いた点。本問題では混在運用を「壊してはならないもの」として扱い、選択の置き場所の解決は設計に委ねる）
- **正しく用意できたかが公開してみるまで分からない**: 認証情報が無い・通らない・GitHub に届かないときは、公開ステータスが unknown になり、公開・取り込みが失敗として伝わる。用意の時点で確かめる経路は無い
- **git 手段には別の前提がある**: git 手段を選ぶことは可能だが、その前提（git のインストール・clone 済み・upstream 設定）を満たすことは本問題の範囲外。選択肢として見せる以上、前提が満たせない環境で選ばれうる

### 観察された症状

- 作者が GitHub 手段で運用を試すのに、`.blog/credentials.json` の存在と形式を Claude に聞かなければ分からなかった（F-03）
- `blog.json` に `publish.means: "github"` と `github.owner/repo` を手で書く必要があり、これは spec の該当節を読んで初めて分かる
- 「このシステムで何ができるか、ユーザーは何もわからない」——作者自身にとってもそうだった。能力（git 無しでの GitHub 経由運用）は備わっているのに、それを知る手がかりがアプリの中に無い

これらは表層であり、背後にあるのは「手段を選ぶ・認証情報を用意する、という行為がアプリの中に存在しない」ことである。

## 範囲外

- **既存ブログを git 無しマシンで始める（clone 相当）**: 空フォルダにリモートの内容（原稿・資材）を実体化すること。別問題（gitless-existing-blog-onboarding、未作成）。本問題は「原稿フォルダが手元にある」ところから始まる
- **新規ブログを git 無しマシンで始める**: 資材一式（テンプレート・CSS・ヘルパー・package.json・デプロイの設定）の生成、空リモートへの最初の到達（F-02）、リモート側のビルド・デプロイの前提の明示化（F-04）。別問題（gitless-new-blog-onboarding、未作成）
- **GitHub 側の操作そのもの**: アカウント・リポジトリの作成、トークンの発行、Pages の有効化。ただし「トークンをどこでどう発行するか」の案内は本問題の内側
- **git 手段のセットアップ**: git のインストール・clone・upstream 設定・credential helper。選択肢として git 手段が見えることは範囲内だが、その前提を満たす手伝いは範囲外
- **native app 固有の設定画面**: エディタの中に作る。native app 側の設定 UI は作らない
- **blog.json の publish 以外の項目の構成**: 本問題は公開手段に関わる設定に限る（サイト名等の一般設定の UI 化は扱わない）
- **同期操作そのものの振る舞い**: 公開・非公開・削除・取り込みは既存のまま。手段が替わっても意味は変わらない（gitless-publication-means で達成済み）
- **差分の可視化・分岐の脱出路**: sync-diff-preview の範囲

## 解決したと言える状態（問題領域の言葉で）

- 作成者は、設定ファイルの存在・形式を知らずに、アプリの中の操作だけで公開手段を選び、GitHub 手段に要るリモートの識別を与えられる
- 作成者は、アプリの中の操作だけで認証情報を用意・差し替えでき、トークンの発行の仕方がアプリの中で案内されている
- 用意された認証情報が手元だけに置かれ、共有設定にもリモートにも含まれない、という既存の保証が保たれている
- 手元に原稿フォルダがあり、リモートに資材一式がある状態から、選択と用意を終えれば、既存の同期操作の一式（公開・更新・非公開・削除・取り込み）が選んだ手段で、git 手段のときと同じ意味で動く
- 手段を選ぶ操作を通じて、「git 無しでも GitHub 経由で運用できる」ことが作成者に分かる
- 同じリモートを共有する別のマシンの運用（git 手段のマシンとの混在）が、本問題の選択によって壊れない
- web のエディタに作られ、native app にもそのまま載る
- **この問題で新しく成立する行為**: 「作成者は公開手段を選択できる」「作成者は認証情報をアプリの中で用意できる」。成立条件が広がる既存の行為: 無し（act-0008「公開手段を意識せずに記事を公開できる」の意味は変わらない——選ぶのは運用の始めであり、日々の公開で手段を意識しないことは保たれる）

## 技術的背景（調査結果）

- **手段の決定**: `公開手段解決器`（lib/publishing/publicationMeansResolver.js）が blog.json の `publish.means` を読み、`git`（既定）または `github` を組み立てる。`github` のときは `publish.github.{owner, repo, branch, api_base}` と認証情報提供者を渡す（docs/spec.md#editor パッケージ — 公開手段の設定）
- **認証情報の供給**: `認証情報提供者`（lib/publishing/credential.js）はコンテンツルート内 `.blog/credentials.json` から手段名（`github`）で区切られた `{ token }` を読むだけ。無い・読めないときは null。書き込む経路は無い
- **無い・通らないときの伝わり方**: 公開ステータスが `unknown` になり、公開・取り込みは失敗として伝えられる（spec 同節）。用意の時点で確かめる経路は無い
- **エディタの現状**: サイドバー・編集・画像ライブラリ・公開操作の UI はあるが、設定に類する画面は無い。エディタの新しい画面は「URL が資源を特定し、表示は URL から再構成される」というエディタのナビゲーションモデルに従うのが既定（editor コンテキストの設計方針）。native app（native/）はこの web エディタをシェルとして表示するため、エディタ側に作れば載る
- **blog.json の性格**: 共有設定であり、git 運用ではリモートにコミットされる。GitHub 手段でも `公開対象` ではないのでリモートへは送られないが、git 手段のマシンからは手元差分として見える。手段の選択がここに書かれる限り、選択は「そのリモートを使う全マシンの手段」を意味する
- **なぜ問題を生んでいるか**: gitless-publication-means v2 は「認証情報の獲得フロー」と「初回セットアップ」を範囲外に置き、「用意されているところから始まる」設計にした。手段の追加そのものは達成されたが、その手段に到達する行為が利用者に開かれておらず、能力の存在が見えない

## /tdd-run への申し送り

- **語彙定義の種**: 公開手段の選択（構成として決まっていた手段を、作成者の行為にする）。認証情報の用意／登録（`認証情報` の現行定義「獲得のフロー（認証 UI）は範囲外で、用意されているところから始まる」の改訂が要る——用意する行為が内側に入る）。トークン発行の案内（アプリの外の操作を、アプリの中から辿れるようにするもの）
- **開いている点（選択の置き場所）**: 手段は共有設定（blog.json＝リモートの属性）で決まるが、「git があるか」はマシンの性質。作成者がアプリで選んだ手段を共有設定に書くのか、手元だけの設定にするのか、両方を組み合わせるのか。混在運用（同じリモートを git 手段と GitHub 手段のマシンで使う）を壊さないことは解決条件に含めた
- **開いている点（用意の時点での確認）**: 登録した認証情報がリモートに届くかを、公開する前に確かめる経路を設けるか。設けるなら「届く／届かない」の読みは既存の unknown・失敗と同じ言葉で伝わるべき
- **開いている点（画面上の扱い）**: 認証情報を画面でどう扱うか（再表示しない・差し替えのみ、等）。「手元だけに置く」の保証と、画面に出すことの両立
- **開いている点（git 手段の見せ方）**: git 手段を選択肢として見せるとき、その前提（clone 済み等）が満たせない環境で選ばれた場合に何を伝えるか。前提を満たす手伝いは範囲外
- **範囲の確認**: 「blog.json を UI 上で構成できる」を本問題では公開手段に関わる設定に限った。一般設定への拡張は別問題
- **利用検証の基準**: 作者自身が、原稿フォルダが手元にあり資材一式のあるリモートが存在する状態から、設定ファイル（blog.json・.blog/credentials.json）を一切手で触らずに GitHub 手段の運用を始められるか。native app への搭載は後続問題（既存ブログ／新規ブログの始め方）の検証で確かめる
- **後続問題への橋渡し**: 本問題で「選ぶ・用意する」が作成者の行為になれば、既存ブログの始め方（clone 相当）は「選んで用意した手段でリモートから実体化する」、新規ブログの始め方は「選んで用意した手段で資材一式をリモートに置く」として、同じ入口の続きに置ける
