# 公開

原稿がサイトとして公開された状態に至るまでの流れ（公開ステータスの判定・リモートへの反映・デプロイ）を、公開手段から独立に定義する。手段が替わっても、公開する・公開ステータス・同期の各操作の意味は変わらない。

## 公開手段による公開

ローカルにある原稿は、リモートに反映されてはじめて公開となる（保存はローカルへの書き込みのみで、公開とは別操作）。この反映を実現するのが公開手段で、リモートの実体、リモート状態（リモートの内容を参照する読み取り専用の抽象）、反映・除去・取り込みの実行、版の連なりの参照、リモートの知識の更新、認証情報の扱い、送る公開物の形態（原稿か成果物か）を一まとまりで担う。公開手段解決器が構成にもとづいて使う手段を決め、エンドポイントは手段を直接組み立てない。

どの手段も原稿を公開物として送り、ビルドとサイトへの実反映はリモート側のデプロイ（外部の CI/CD）に委ねる。反映が完了した時点で公開操作は完了とみなされ、サイトへの実反映は非同期に起きる。CI/CD の設定・変更はこの領域の範囲外。

- **git公開手段**（既定）: 手元の git でリモート状態の参照・反映・除去・取り込みを行う。版の連なりは git の履歴から得る。
- **GitHub公開手段**: 手元に git を要求せず、GitHub接続（認証情報を添えた読み書きの口）越しにリモートを直接読み書きする。記事と参照画像を一度の反映でまとめて届け、リモートの更新は git 運用の反映と見分けがつかない形（履歴が一本、内容が同じ）で行う。反映・除去しようとするファイルについてリモートが進んでいれば、上書き・消去せず何も書かずに拒み、先に取り込みが要ることを伝える。git の履歴が担っていた「前回揃えた時点」の知識は同期の基点として自身が保持し、フィンガープリント（内容から計算され、リモート側の識別と一致する値）で内容を取り寄せずに手元とリモートの同異を判定する。

### 設定 — `blog.json` の `publish`

| `publish.means` | 前提 |
|---|---|
| `git`（既定・省略時） | 手元に git があり、コンテンツルートが clone 済みで upstream が設定されている |
| `github` | GitHub がホストするリモートと、そこへ届く認証情報 |

| キー | 必須 | 既定 | 意味 |
|---|---|---|---|
| `publish.github.owner` / `repo` | ○ | — | リモートの識別 |
| `publish.github.branch` | | `main` | 反映先のブランチ |
| `publish.github.api_base` | | `https://api.github.com` | API の入口（GitHub Enterprise 等） |

```json
{ "publish": { "means": "github", "github": { "owner": "<所有者>", "repo": "<リポジトリ名>", "branch": "main" } } }
```

手段はリモートの属性として共有設定（blog.json）で決める。同じリモートに対して git 運用のマシンと GitHub 手段のマシンが混在してよい。

### 認証情報

公開手段がリモートへ届くために示す本人性の証し。コンテンツルート内の `.blog/credentials.json` に手段名で区切って置き、blog.json にもリモートにも含めない（手元だけに残るファイル。git 運用のマシンでは `.gitignore` に `.blog/` を加える）。獲得のフロー（認証 UI）は範囲外で、用意されているところから始まる。

```json
{ "github": { "token": "<対象リポジトリの contents 読み書き権限を持つトークン>" } }
```

### 失敗時

- 手段名が未知、または GitHub 手段でリモートの識別が無いとき、公開手段の解決は失敗する。リモート状態解決器はエディタ全体を止めず、参照不能なリモート状態を返してログに残す。
- リモートが参照不能なとき（手段名の誤り／upstream 未設定／認証情報が無い・通らない・不通）、公開ステータスは判定不能となり、原因を問わず同一に扱われて、公開・非公開・削除・取り込みのいずれの操作も行えない。
- 公開操作そのものが失敗したときは、その理由が公開フィードバックとして伝えられる。

## 同期

ローカルとリモートの内容を揃える操作の総称。届ける向き（公開する・更新する）、取り除く向き（除去）、取り込む向き（取り込む）がある。編集中のファイル単位に縛られず、両場所の全体を対象にできる。

**除去は一操作一場所。** 非公開にするはリモートからの除去（原稿は手元に残り、再公開できる）、削除するはローカルからの除去（未公開であることが前提）。二つの場所にまたがる除去や削除の伝播は存在せず、公開済みの記事を消すには非公開にする → 削除するの二段になる。一度公開したファイルと一度も公開していないファイルは、どちらも「未公開」として区別しない。

**内容差分と版の連なり。** 内容比較だけから言えるのは一致・不一致・欠如までで、向きは言えない。公開ステータスはこの読みにあたる。先行・後行・分岐という向きと、手元に無いファイルの事情（手元で消された／他所で作られた）は、版の連なり（版の履歴と共通の祖先の知識）があって初めて言える。版の連なりは公開手段への要求とし、git は履歴から、GitHub 手段は同期の基点から得る。満たさない手段では、両側に存在して内容が異なるものを分岐として扱い、不一致までで正直に退化する（取り込みで執筆内容を失わないため）。

**取り込む。** リモートの知識を更新したうえで、リモートに存在するファイルのうち原稿の範囲（`src_dir` 配下）だけを候補にし、記事ごとに版の連なりを判定する。他所で作られた・リモートが先行しているものは取り込む。分岐しているもの・手元で消されたものは見送り、その理由を執筆者の言葉で返す。同じ・手元のみ・手元が先行のものは対象外。手元の執筆内容は上書きしない。

### 同期の基点（GitHub 手段）

手元とリモートを最後に揃えた時点の、ファイルごとの内容の知識。コンテンツルート内の `.blog/sync-base.json` に置かれ、リモートへは送られない。そのファイルの公開・除去がリモートに届いたとき、および取り込みで手元に反映されたときにファイル単位で進む（除去が届いたときは記録が消える）ので、部分的な取り込みでも他のファイルの判定が壊れない。`.cache/` と違い、消すと手元で編集しただけの記事が分岐扱いに退化するので消さない。

基点の記録がまったく無いコンテンツルート（clone 済み相当のフォルダを初めて開いた）では、最初に手段を組み立てたときにリモートと同じ内容のファイルすべての基点をまとめて揃える。以降は差分判定で「同じ」と分かった時点でファイルごとに揃える。初回接触より前にリモートだけが進んでいたファイルは基点が無く、分岐扱いになる。

**具体例:** 公開 → 非公開 → 削除 → 別マシンで公開された記事の取り込み、の一巡が git コマンドを打たずにエディタ内で完了する。

## 行為

- 作成者は、公開手段を意識せずに記事を公開でき、公開状態が参照できないときは操作できない理由が分かる。
- 作成者は、公開した記事を、原稿を手元に残したまま非公開に戻せる。
- 作成者は、未公開の記事を削除できる。
- 作成者は、リモートの内容を手元に取り込める。
